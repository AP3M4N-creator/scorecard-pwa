Five things did not go as written, and the code says so at each site:

- **The finding looked at the wrong control for F27.** The proposed fix is an overlay on the

  edge to edge, so there is no gap to grow into, only height. The real find was in the batting

  was not a target at all, and tapping the empty part of a cell did nothing. Pinning the
  controls to their cells took the position select to 38×58 and the name field to 155×58 at no

  did not move: measured, the drift is 0.00px on all four.
- **F28's one-line fix broke the layout it was protecting.** Excluding the phone from the iPad
  block is correct and is one line; what the finding did not say is that the phone-landscape
  block had been *depending* on the rules it was inheriting. Its own note says the strip "stays
  one row, as it is above 835px" — and the rule making it a row was arriving from the iPad. With
  the two separated the strip went 137px → 244px, the scoreboard stopped being sticky, and the
  batting grid started 113px further down a 390px screen. Eleven rules are restated in that
  block now, measured back to identical, with two deliberate differences (an inset-aware bleed,
  and a 78px name column). One of them is a rule the iPad sets that this block must *not* copy —
  a narrower block already had `.live-label` at 8px and copying the iPad's 9px cost 2.7px of
  strip. Restating everything would have been as wrong as restating nothing.
- **F33's verification could not be run, and the finding is stronger for it.** "Check that
  `transitionend` still fires rather than assuming it" cannot be checked in an undisplayed
  Browser pane: nothing composites, so no transition runs at all and the question cannot be put.
  What is written down instead is why the app does not need the answer — `ui.js` already
  re-measures on the handle's own click, one frame later, by which time a 0.01ms transition has
  finished and a 200ms one has not. So the event is redundant under reduced motion and
  load-bearing without it, which is the right way round.
- **`npm test` was never letting the page finish loading.** Found while writing the `ui.js`
  cases, and it is the largest thing in this wave. The JSDOM constructor returns with
  `readyState` still `loading`; the runner appended the suite right there, so **no
  DOMContentLoaded or load handler in the app had ever run under `npm test`**. `ui.js` wraps
  `switchTab` on DOMContentLoaded — that is what moves the single Notes box between the two team
  cards — so the feature worked in a browser and was untestable here. The runner is async now
  and waits. jsdom also ships no `matchMedia`, which `fit()` asks three questions, and a throw
  inside a `requestAnimationFrame` callback fails nothing and prints nothing: the fit engine
  would have thrown on every frame in silence.
- **The `git stash -k` fix, written the way everyone writes it, corrupts the working tree.**
  `git stash push --keep-index` stashes the staged *and* unstaged changes and then restores the
  index, so a plain `git stash pop` re-applies a diff over a tree that already has half of it.
  Where both halves touch one file that conflicts and leaves `<<<<<<<` markers in the file the
  hook was protecting. Watched it happen in a throwaway repo, which is the only reason it is not
  in the hook. The restore resets to HEAD first — making the pop a fast-forward — and pops with
  `--index` so the staged/unstaged split comes back intact. Proven over three cases: both halves
  touching one file with the run passing, the same with it failing, and a clean tree with an
  unrelated stash that must not be touched.

**`--gold` is the one thing left open inside a closed finding.** It has 24 call sites and every
one of them wants "whatever reads on the navy ground", which in this skin is white — so the
*value* is right at all 24 and it is the *name* that lies. Renaming it to `--on-navy` was ruled

## Tier 1 — things that do not work at all

### F22 — the Game Summary's **change** links open a popup behind the modal

**Symptom.** Finish any game. The summary opens by itself and offers `W: … change`,
`L: … change`, `SV: — change`. Tap any of the three. **Nothing appears to happen.** The popup
is open — it is just painted underneath the summary, and the summary is still tappable on top
of it, so the next tap lands on a box-score cell.

All three links are dead the same way, on every finished game. This is the only route to
overriding a pitcher decision, so the feature is unreachable.

**Root cause.** Two stacking ladders that were authored independently (F29).
`promptPitcherDecision` builds `#decision-popup` with `z-index:400` and appends it to
`document.body` (app.js:7329-7331). The summary it was opened from is
`.game-summary-modal { z-index: 600 }` (styles.css:618), also a fixed body child. 600 wins.

Measured live at 1194×834, with the summary open and `change` pressed:

```
zIndex: { summary: "600", decisionPopup: "400", backdrop: "180" }
decisionPopup: display:block, 240x156 at (470,339)
document.elementFromPoint(590, 417) -> <td> inside #game-summary-modal
```

The backdrop makes it worse rather than better: `decision-popup` is in `ALSO_GUARDED`
(app.js:1647) so a backdrop goes up at `z-index:180` — below *both* — leaving the summary
fully interactive while a modal popup is open and invisible behind it.

**Fix.** The popup has to outrank the surface it was opened from. Smallest correct change:

```js
// app.js:7331 — opened from inside the summary (z-index 600), so it has to clear it.
popup.style.cssText = 'position:fixed;top:50%;left:50%;transform:translate(-50%,-50%);…;z-index:700;…';
```

Do not fix this one in isolation — take F29 with it, or the next popup opened from a modal
lands in the same hole. If F29 is deferred, at minimum lift `decision-popup` above 600 and
lift `#popup-backdrop` (app.js:1682) above the summary too, so the guard actually guards.

**Verify.** Browser: finish a game, press each of the three `change` links, confirm the popup
is visible and that `document.elementFromPoint` at its centre is inside `#decision-popup`.
Test: assert `zIndex(decision-popup) > zIndex(.game-summary-modal)`, and that
`elementFromPoint` at the popup's centre resolves into the popup. A jsdom test can only check
the numbers, not the paint — say so in the test name.

**Risk.** Low. One number, plus whatever F29 settles.

**Landed** out of F29, with no edit of its own — which is what taking the two together was for.
Re-measured against a real finished game (one-inning regulation, home team wins 1–0), pressing
each of the three links:

```
zIndex: { summary: "700", decisionPopup: "800", backdrop: "750" }
decisionPopup: display:block, 240x156 at (470,339)
document.elementFromPoint(590, 351) -> <div id="decision-popup">     (all three links)
document.elementFromPoint(60, 200)  -> <div id="popup-backdrop">     (the summary behind it)
```

End to end as well, not just the paint: picking a pitcher wrote `decisions: {wp: 0}` and the
summary rebuilt reading `W: Pitcher 1`. The other route in is fixed too — a `base-picker`
opened over the Game Library (`.modal-overlay`, 500) resolves at 800 and takes its own taps.

### F23 — an import with an empty `players` array leaves the last game on the card

**Symptom.** Import a file that is valid JSON and has both `info` and `teams` — but whose
`players` arrays are empty (a truncated export, a hand-edited file, an interrupted write).
The import is **accepted**. The team names change to the new file's. The linescore blanks.
And **every player, every position, every pitcher and all 78 play cells from the previous
game are still on screen.** The scorer is looking at one game's plays under another game's
name, with no warning that anything is wrong.

Reproduced live: after importing `{info:{visitingTeam:'X',homeTeam:'Y'}, teams:{visiting:{players:[]}, home:{players:[]}}}`

```
gameState.teams.visiting.players.length -> 0      (and pitchers.length -> 0)
team name inputs                        -> "X" / "Y"
lineup name inputs still reading        -> Altuve, Dubon, Pena, Alvarez, Tucker, Singleton, …
pitcher name inputs still reading       -> Verlander, Pressly, Eovaldi, Leclerc
.play-text cells still filled           -> 78
```

**Root cause.** Two halves, both needed:

1. `mergeStateDefaults` guards with truthiness, and `[]` is truthy — app.js:5104,
   `if (!parsed.teams) parsed.teams = defaults.teams;` passes an empty roster straight
   through, and the top-level `Object.keys(defaults)` merge above it only fills keys that are
   `undefined`. Nothing restores the 27-row / 8-pitcher shape.
2. `applyState` paints rows by walking `players` (app.js:5422-5432). With nothing to walk it
   paints nothing, and never clears the inputs that are already there.

**Landed 2026-08-08**, with five cases. Suite green: **432 passed · 0 failed**.

### F31 — `--font` and `--heading` are identical, and `--mono` never renders

**Symptom.** Read live:

```
--font:    'Graduate', "Source Serif 4", Georgia, serif
--heading: 'Graduate', "Source Serif 4", Georgia, serif      <- byte-identical to --font
--mono:    'Graduate', 'JetBrains Mono', 'SF Mono', Consolas, monospace
```

Two consequences. There is **no body/heading distinction** anywhere in the app — the two
tokens are the same string, so every `font-family: var(--heading)` is decoration with no

load. Graduate is also a single-weight display face with no true italic, so every

The pitch marks, the count and the fielder keypad are all `var(--mono)` — they are the places
tabular figures matter most, and they are getting a display face instead.

**Fix.** styles.css:936-938:

```css
  --font: "Source Serif 4", Georgia, serif;
  --heading: 'Graduate', "Source Serif 4", Georgia, serif;
  /* Graduate has no tabular figures and one weight; the mono stack exists for the pitch
     marks and the count, so it must not start with the display face (F31). */
  --mono: 'JetBrains Mono', 'SF Mono', Consolas, monospace;
```

This one changes how the whole card looks — it is a design decision, not a bug fix. If
Graduate everywhere is the intended house style, then say so and delete JetBrains Mono and its
`@font-face` instead; what should not stand is downloading and precaching a font that cannot
render.

**Verify.** Screenshots of all five viewports, plus a check that the four `@font-face` families
each have at least one element resolving to them.

**Landed 2026-08-08.** Ruled: **Graduate is the house style**, and only `--mono` changes. The
card looks the same — `--font` and `--heading` keep the display face — and the defect the
finding is actually about is closed: JetBrains Mono now renders, so a 31KB font is no longer

timer, the linescore figures and the deck's play buttons.

`--heading` stays byte-identical to `--font` on purpose rather than by accident, and the
declaration now says so: the two names mark intent, and a re-skin that wants them apart has the
seam already cut. A check fails if the display face ever leads `--mono` again.

**And the verification found one more.** "Each `@font-face` family has at least one element
resolving to it" — Source Serif 4 has none, and had none before this either. See **F42**.

**Risk.** Low mechanically, high visually. Wants a ruling before a commit.

### F32 — no overlay is a dialog

**Symptom.** Of the overlay surfaces present in the DOM, **none** carries `role="dialog"`,
`aria-modal`, `aria-labelledby` or `aria-label`. Measured live: `overlaysWithRole: 0`. The
same is true of the fourteen popups built on demand — they are all
`document.createElement('div')` plus a `style.cssText`, with no role and no label.

There is also no focus trap, no focus restoration and no `inert` on the background, so Tab
walks straight out of an open popup into the card behind it, and closing a popup leaves focus
wherever it landed. Across 8,161 lines app.js sets exactly one `role`, two `aria-selected`,
three `aria-current` and two `aria-label`.

The card itself is much better served than the dialogs — `describeCellForScreenReader`,
`announce()` and `#a11y-live` are careful work. It is only the overlays that were left out.

**Fix.** One helper, called from `openPopup` (app.js:1720), so every popup gets it at once
rather than fourteen edits:

```js
function openPopup(popup, labelId) {
  popup.setAttribute('role', 'dialog');
  popup.setAttribute('aria-modal', 'true');
  if (labelId) popup.setAttribute('aria-labelledby', labelId);
  popup.dataset.returnFocus = document.activeElement ? … : '';
  …
```

plus a `keydown` trap on Tab within `blockingPopup()`, and restoring focus in `closePopup`.
Every generated popup already emits a title `<div>` first — give those an id and pass it.

**Verify.** Tests: for each popup id, assert `role="dialog"` and `aria-modal="true"` after
`openPopup`, and that `aria-labelledby` points at an element with text. Tab-cycling and focus
restoration need a browser check.

**Risk.** Low if done in `openPopup`. Do not do it fourteen times.

**Landed 2026-08-08**, with ten cases. Suite green: **442 passed · 0 failed**. It was done in
`openPopup` — role, `aria-modal`, label, focus in, focus back, and a Tab trap — plus the three
`active`-class modals, which do not go through `openPopup` and so could not pick any of it up
from there. Eighteen overlays in all.

Five things worth writing down:

1. **The labels are derived, not passed.** The fix suggested giving fourteen title `<div>`s an
   id and passing each one in. They did not need to be: **all fifteen popups open with their
   title as the first element**, including `k-popup` ("Strikeout") and `spray-popup`, whose
   title is an `<h3>` in `index.html` rather than anything app.js builds. So `labelPopup` takes
   it from there and assigns the id itself. The convention is not assumed — a case walks the
   real open paths and fails if a popup stops holding to it, which is the assumption made
   checkable rather than left in a comment.
2. **`aria-modal="true"` is true of all fifteen**, which is worth stating because it would be a
   lie otherwise: `PENDING_ENTRY_POPUPS` + `ALSO_GUARDED` is exactly the fifteen, so every one
   of them really does have the backdrop over the card behind it.
3. **The trap steps every Tab itself**, not only the two that wrap. That way the cycle is
   exactly the list the trap is enforcing, with no second implicit order to disagree with it —
   and it is why "Tab-cycling and focus restoration need a browser check" turned out not to be
   so. Both are covered under `npm test`.
4. **Focus goes to the container, not the first control.** Focusing a button would have the
   reader announce the button and skip the label the dialog had just been given.
5. **`contains` counts a node as containing itself**, so focus resting on the container read as
   "already inside the cycle" and the first Tab did nothing. Caught by the case, not by
   reading — it is the kind of thing that looks right on the page.

Blocked options (F26) drop out of the tab order for nothing, because they are `disabled`; a
case asserts that, and that the reason for the block is still on the page rather than only on a
control that can no longer be reached.

**Not done: `inert`.** The symptom names it alongside the trap. `aria-modal` plus the trap
covers assistive tech and the keyboard, and the backdrop already covers the pointer, so what
`inert` would add here is a third statement of the same thing — but it is the one part of the
finding left standing, and it is written down rather than quietly dropped.

### F38 — the pre-commit hook lost its executable bit, and its `sed` never worked

Two separate things:

1. The entire diff to `.githooks/pre-commit` is `old mode 100755 / new mode 100644` — no

(app.js:3343), an undo restoring the other team (app.js:4230) — so the first case that ends on
Home leaves every later case running against `#tab-visiting`, which the stylesheet has at
`display: none`.

Under `npm test` that is harmless and undetectable: `run-tests.js` builds its JSDOM without
`resources: 'usable'`, so styles.css never loads, nothing is hidden, and every selector still
resolves. In a browser an element inside the inactive tab has no `offsetParent` and **cannot
take focus at all**.

Instrumented over a full run at `1446cc1` — every `focus()` on a lineup name field:

```
32 calls,  2 took focus,  30 did not
the 30:  ownTab tab-visiting  active false  display none  offsetParent false
the  2:  ownTab tab-visiting  active true   display block offsetParent true
```

So `document.activeElement` assertions after the first tab switch were not checking what they
read as checking, and two of the F7 SUB cases were failing outright. The two that worked did so
only because of where they sat in the file.

**Fix.** In `reset()`, alongside the regulation select — guarded on the class, because
`switchTab` issues three uncached document-level queries and at ~6ms each under jsdom that is
~7s added to a 400-case run to undo something most cases never did:

```js
  const vTab = document.getElementById('tab-visiting');
  if (vTab && !vTab.classList.contains('active') && typeof switchTab === 'function') {
    switchTab('visiting');
  }
```

**Verify.** Done: `SUB opens the row it just created and puts the caret in it` goes green at
`1446cc1` with only this change, which is the proof it was the tab and not the app.

**Risk.** None to the app — the file is test-only. It does make ~30 assertions start meaning
what they say, so if one of them is wrong about the app, this is what will surface it. None
did.

## Tier 7 — raised by wave 4's own verification, 2026-08-08

Neither of these is a defect anyone will see. Both are decisions, and both were found by running

### F42 — Source Serif 4 is precached and never renders

F31's verification step is "a check that the four `@font-face` families each have at least one
element resolving to them". Run after F31 landed, JetBrains Mono passes — that was the point of
the fix — and **Source Serif 4 does not**. It leads no stack. It is second in `--font` and
`--heading`, behind Graduate, and it exists as the fallback so a missing woff2 degrades to the
broadsheet skin rather than to system-ui.

```
first family in the resolved stack, walked over every laid-out element:
  Graduate         body, .app, .deck-strip, …
  JetBrains Mono   .timer-display, .linescore input, .quick-btn, .ls-sub
  Source Serif 4   (none)
```

The wrinkle is that the fallback cannot fire in a working install. `sw.js` precaches all four
faces in one `addAll`, which is all-or-nothing: either every font is in the cache — Graduate
included, so it cannot fail — or the install failed and none of them are. So the two Source
Serif files are 2 of the 4 precached faces, paying off only in a state the service worker is
designed to prevent.

Not a bug: `sw.js:13` already says Source Serif "stays on as its fallback", so this is a cost
that was chosen. It is written down because F31 was the same shape — a font shipped and never
rendered — and the reason the two are different is worth being explicit about rather than
assumed. **Decide it; do not inherit it.** Either drop the two files from the precache list and
let the fallback be a network fetch on the day it is ever needed, or keep them and say here that
the redundancy is worth ~40KB.

**Risk of acting.** Low. It is the `FONTS` array in `sw.js` and nothing else; the `@font-face`
rules stay either way. The delivery check that every precached asset exists still passes.

### F43 — the home-field constant does not produce the win rate it claims

`winProbFromDiff` carried `const hfa = 0.18; // ~54% home win rate at start`. It does not
produce one:

```
sigma at the first pitch = sqrt(18) * 0.92 = 3.904
z = 0.18 / 3.904 = 0.0461
winProbFromDiff(0, 18) = 0.5184        <- 51.8%, not 54%
```

54% is roughly the real-world home win rate, so the intent is clear and the arithmetic was never
checked against it. Reaching 54% at nine innings wants `hfa` ≈ 0.39.

**Not changed.** The constant sits under every point of every curve this app draws, and moving it
re-draws every summary ever produced from a saved card — that is a modelling decision, not a
typo fix, and wave 4 was chartered for coverage. What landed instead: the comment now states
what the constant actually does and what it was aiming at, and a case pins 51.8% so that
changing it is something somebody decides rather than something that drifts.

**Risk of acting.** Low mechanically — one number — and it changes the shape of every chart, so
it wants the same kind of ruling F31 got.

### F44 — the card does not quite fit at 1194×834, and never has

Found 2026-08-08 on the deployed site, after wave 4 — and only findable then. Every earlier
measurement in this document was taken with `fit()` never having run, because
`requestAnimationFrame` does not fire in an undisplayed Browser pane (F40). Wave 4 handed `fit`
out on `window.__ui` so the suite could call it synchronously, and the same seam makes it
callable in a browser: the boxes are really laid out, so the arithmetic is real even though no
frame is being painted. Calling it is what showed this.

**Symptom.** At 1194×834 — the 11" iPad in landscape, the viewport this whole layout is built
around — the page scrolls by 2px.

```
1194x834   --cell-h 44px (its floor)   --deck-h 177px   page scroll 2px
1024x768   --cell-h 48px               --deck-h  63px   page scroll 0
834x1194   --cell-h 55px               --deck-h 119px   page scroll 0
390x844    --cell-h 48px                                page scroll 0
844x390    --cell-h 48px                                page scroll 0
```

Two pixels, and `ui.js` is explicit that this is the failure it cares about: `PAD` is 18 rather
than 16 precisely because "short-changing it leaves the page 2-3px scrollable, which on a touch
screen is as annoying as 300px". The whole point of the one-page fit is that the scoreboard, the
inning headers and the deck never move under the scorer's finger, and a 2px scroll means they
can.

**Root cause — the flat drawer, not the fit engine.** At ≥1100px the More-plays drawer stops
being a drawer and lies open permanently (F9), and `fit()` correctly reserves the whole deck
there rather than just its core. That is 177px, which is 20px more than the F9 note's own
measurement of 164px. With that much reserved, nine rows cannot be fitted: `--cell-h` clamps to
its 44px floor and the page is still 2px over. Everywhere else there is slack and the scroll is
zero.

Isolated rather than assumed. Folding the drawer at the same viewport:

```
drawer flat (resting state)   --cell-h 44px   --deck-h 177px   scroll 2px
drawer collapsed              --cell-h 54px   --deck-h  78px   scroll 0
```

**Not caused by wave 4**, checked directly: putting the linescore's row height back to its
pre-F27 22px changes neither number (`--cell-h` 44, scroll 2, strip 97px either way), because
F27 spent height the strip's column was already holding open and the strip's own height never
moved.

So this predates the audit and has been shipping since F9 landed. It is invisible to the suite —
jsdom has no layout — and was invisible to the review, which could not run `fit()`.

**Fix.** Not obvious, and it is a trade rather than a number, which is why it is written up
instead of fixed:

- Give the floor 2px (`FIT_MIN` 44 → 42) and the card fits, at the cost of a seven-mark pitch
  column at 5.4px. `ui.js` already argues against exactly this for the phone.
- Or fold the flat drawer by default at 1194 and let the button open it. That hands back 99px
  and takes rows to 54px, but it undoes the thing F9 was for — all 33 plays on screen at once.
- Or find the 2px. `--deck-h` is 177 where F9 measured 164; something in the deck grew by ~13px
  after that note was written, and it may simply be recoverable.

The third is the one worth trying first, and none of them should be picked without the pane
displayed and a screenshot either side.

**Verify.** Browser at 1194×834: `window.__ui.fit()`, then
`document.documentElement.scrollHeight - clientHeight === 0` with the drawer in its resting
state. Worth a case in the *Stylesheet* section only once the numbers are settled — the suite
cannot measure it, but it can assert `FIT_MIN` has not been quietly lowered.

**Risk of acting.** Medium. It moves the row height at the app's primary viewport, which every
other measurement in Tier 3 is relative to.

> **Done 2026-08-10, by the third option, and it cost nothing.** The 2px was found, and the
> ~13px was never growth: F9's 164 counted the two 46px button rows, the 6px between them and
> the core's 63, and left out the drawer's *own* padding and bottom rule — `8px 0 4px` plus 1px,
> 13px that has been there since F9 landed. Laid flat that padding frames nothing (there is no

>
> ```
> 1194x834, drawer at rest      --deck-h   --cell-h   page scroll
>   before                        177px      44px         2px

> ```
>
> **The card does not move.** The rows were already pinned to their 44px floor and stay there,

> deck's top edge drops 6px, taking the gutter between the last batting row and the deck from

> ```

## Order of work — ruled 2026-08-07

**This is the agreed order.** Waves are sequential and each one assumes the ones before it have
landed; items *inside* a wave are independent and can go in any order, or together. The
ordering is by what unblocks what first, then by value per unit of risk — it is deliberately
not severity order, because two of the cheapest items gate the correctness of every commit
that follows.

### Wave 0 — prerequisites. Nothing below is verifiable without these.

- **F40 — install Node.** Every fix in this document ships with a test and none of them can be
  run. It also re-arms the pre-commit test gate, which currently degrades to a warning
  (`.githooks/pre-commit:16`), so work done before this is not gated.
- **Display the Browser pane.** `requestAnimationFrame` does not fire in a hidden tab, so
  `fit()` never runs. Gates F27, F28, F30, F31 and every before/after screenshot.

### Wave 1 — repo hygiene. Must precede the first code commit.

- **F38** — the hook's exec bit and its `sed`. **First, before anything else is committed.**
  While it is broken no commit touching `app.js`/`styles.css` bumps `SHELL_VERSION`, so every
  fix in Waves 2–4 would ship to a stale cache.
- **F37** — restore `.nojekyll`. One command. Left as-is, Jekyll can drop a font, `addAll`
  rejects, and the PWA silently stops updating — which would mask everything else.

### Wave 2 — dead features and silent presses. Cheap, additive, highest value.

- **F29 + F22 together.** Highest-value item in the document — F22 is a feature that is 100%
  dead on every finished game. Do not do F22 alone: one number fixes this popup and leaves the
  next one opened from a modal in the same hole. Fix the scale and F22 falls out of it.
- **F24** — the `markPinchRunner` tail. Additive; `revealSubRow` is already proven by F7.
- **F36** — `switchTab('visiting')` in `newGame()`. One line.
- **F34** — `.quick-btn small { opacity: .7 }`. One declaration.
- **F35** — settle the theme colour in all three places, including the `var(--navy, #1a2744)`
  fallbacks that carry a superseded palette into every generated popup.

### Wave 3 — real bugs, each landing with its test.

- **F23** — land it *with* the first `importGameJSON` test. That test is as much the
  deliverable as the fix; it touches every load path, and the round-trip assertion is what
  makes the padding safe.
- **F26** — do it immediately before F25. Same popup, and it makes F25 easier to test.
- **F25** — riskiest in this wave. The rollback has to take back the play *and* the result
  pitch; follow F11b's caller-supplied shape rather than inventing a second one.
- **F32** — one central edit in `openPopup` covers all fourteen popups. Deliberately **after**
  F29 so popup construction is not touched twice.

### Wave 4 — needs a ruling before any code is written.

These are not judgement calls to be made in passing.

- **F31** — is Graduate-everywhere the house style, or should `--mono` really be JetBrains Mono
  and `--heading` differ from `--font`? Either answer is fine. What should not stand is
  precaching a font that cannot render.
- **F30** — collapse the three `:root` blocks. No behaviour change is intended, so the check is
  that nothing moved: screenshot all five viewports before and after and diff.
- **F27** — bigger hit areas against the one-page fit. A real trade, and the fit is the feature.
- **F28** — making the two blocks disjoint changes which rules apply at 844×390, so the whole

- **F33** — trivial CSS, but `ui.js` listens for `transitionend` to trigger `refit()`. Check
  that it still fires rather than assuming it does.
- **F39** — scope. The `importGameJSON` test arrives free with F23; inlining `ui.js` into the
  harness and testing the win-probability maths are separate pieces of work.

**Single starting point, if only one thing gets done:** Wave 0, then F38, then F37, then
F29+F22. That takes the cache-versioning hazard off the table and turns a completely dead

Waves 1 and 2 are the only ones landable without displaying the pane — Node aside, for the

## Tier 1 — things that do not work at all

### F22 — the Game Summary's **change** links open a popup behind the modal

**Symptom.** Finish any game. The summary opens by itself and offers `W: … change`,
`L: … change`, `SV: — change`. Tap any of the three. **Nothing appears to happen.** The popup
is open — it is just painted underneath the summary, and the summary is still tappable on top
of it, so the next tap lands on a box-score cell.

All three links are dead the same way, on every finished game. This is the only route to
overriding a pitcher decision, so the feature is unreachable.

**Root cause.** Two stacking ladders that were authored independently (F29).
`promptPitcherDecision` builds `#decision-popup` with `z-index:400` and appends it to
`document.body` (app.js:7329-7331). The summary it was opened from is
`.game-summary-modal { z-index: 600 }` (styles.css:618), also a fixed body child. 600 wins.

Measured live at 1194×834, with the summary open and `change` pressed:

```
zIndex: { summary: "600", decisionPopup: "400", backdrop: "180" }
decisionPopup: display:block, 240x156 at (470,339)
document.elementFromPoint(590, 417) -> <td> inside #game-summary-modal
```

The backdrop makes it worse rather than better: `decision-popup` is in `ALSO_GUARDED`
(app.js:1647) so a backdrop goes up at `z-index:180` — below *both* — leaving the summary
fully interactive while a modal popup is open and invisible behind it.

**Fix.** The popup has to outrank the surface it was opened from. Smallest correct change:

```js
// app.js:7331 — opened from inside the summary (z-index 600), so it has to clear it.
popup.style.cssText = 'position:fixed;top:50%;left:50%;transform:translate(-50%,-50%);…;z-index:700;…';
```

Do not fix this one in isolation — take F29 with it, or the next popup opened from a modal
lands in the same hole. If F29 is deferred, at minimum lift `decision-popup` above 600 and
lift `#popup-backdrop` (app.js:1682) above the summary too, so the guard actually guards.

**Verify.** Browser: finish a game, press each of the three `change` links, confirm the popup
is visible and that `document.elementFromPoint` at its centre is inside `#decision-popup`.
Test: assert `zIndex(decision-popup) > zIndex(.game-summary-modal)`, and that
`elementFromPoint` at the popup's centre resolves into the popup. A jsdom test can only check
the numbers, not the paint — say so in the test name.

**Risk.** Low. One number, plus whatever F29 settles.

### F23 — an import with an empty `players` array leaves the last game on the card

**Symptom.** Import a file that is valid JSON and has both `info` and `teams` — but whose
`players` arrays are empty (a truncated export, a hand-edited file, an interrupted write).
The import is **accepted**. The team names change to the new file's. The linescore blanks.
And **every player, every position, every pitcher and all 78 play cells from the previous
game are still on screen.** The scorer is looking at one game's plays under another game's
name, with no warning that anything is wrong.

Reproduced live: after importing `{info:{visitingTeam:'X',homeTeam:'Y'}, teams:{visiting:{players:[]}, home:{players:[]}}}`

```
gameState.teams.visiting.players.length -> 0      (and pitchers.length -> 0)
team name inputs                        -> "X" / "Y"
lineup name inputs still reading        -> Altuve, Dubon, Pena, Alvarez, Tucker, Singleton, …
pitcher name inputs still reading       -> Verlander, Pressly, Eovaldi, Leclerc
.play-text cells still filled           -> 78
```

**Root cause.** Two halves, both needed:

1. `mergeStateDefaults` guards with truthiness, and `[]` is truthy — app.js:5104,
   `if (!parsed.teams) parsed.teams = defaults.teams;` passes an empty roster straight
   through, and the top-level `Object.keys(defaults)` merge above it only fills keys that are
   `undefined`. Nothing restores the 27-row / 8-pitcher shape.
2. `applyState` paints rows by walking `players` (app.js:5422-5432). With nothing to walk it
   paints nothing, and never clears the inputs that are already there.

Note this is not import-only: `loadState` runs the same merge, so a truncated
`localStorage` card does the same thing at boot.

**Fix.** Restore the shape in the merge, where every load path shares it:

```js
  if (!parsed.teams) parsed.teams = defaults.teams;
  // `[]` is truthy, so the guard above lets a truncated roster through — and applyState
  // paints rows by walking `players`, so an empty one leaves the last game's names on
  // screen under the new game's title (F23).
  ['visiting', 'home'].forEach(t => {
    const d = defaults.teams[t];
    if (!parsed.teams[t]) parsed.teams[t] = d;
    const p = parsed.teams[t];
    if (!Array.isArray(p.players) || p.players.length < d.players.length) {
      p.players = d.players.map((def, i) => (p.players && p.players[i]) || def);
    }
    if (!Array.isArray(p.pitchers) || p.pitchers.length < d.pitchers.length) {
      p.pitchers = d.pitchers.map((def, i) => (p.pitchers && p.pitchers[i]) || def);
    }
  });
```

**Verify.** Test (this is the first test `importGameJSON` will have — see F39): import a
payload with `players: []`, assert `players.length === ROWS_PER_POS * POSITIONS`, that every
name input is empty, and that no `.play-text` cell has content. A second test that a real
round-trip export still imports byte-identical, guarding the padding.

**Risk.** Low, but it touches every load path — the round-trip test is the one that matters.

## Tier 2 — the silent-refusal family, unfinished

`FIX_PLAN.md` spent F3, F7 and F11 establishing one rule: *a press either does something or
says why not.* Three places never got the memo, and in two of them the fix already exists a

### F24 — PR shows nothing at all

**Symptom.** Put a man on. Select his cell. Press **PR**. Nothing happens: no toast, no mark,
no caret, no visible row. The pinch runner *is* recorded — but the row that holds his name is
`visibility: collapse` until it has one, and nothing offers you the chance to type it. The
only way in is "Show sub rows", far right of the section bar, which the press does not point
at.

This is F7 word for word. F7's own comment (app.js:5955-5960) describes this symptom and says
the fix is that one tap should land the caret where the name goes.

**Root cause.** `markSub` (app.js:5945) ends with `revealSubRow()` + `announce()` +
`showPlayNotice()`. `markPinchRunner` (app.js:6008) ends with `announce()` **only** —
app.js:6037. No `revealSubRow`, no `showPlayNotice`.

Measured live, same card, same conditions, PR on slot 1 against SUB on slot 4:

| | **PR** | **SUB** |
|---|---|---|
| row class | `pos-sub` | `pos-sub revealed` |
| computed visibility | **`collapse`** | `visible` |
| caret | **`document.body`** | the name input |
| visible toast | **none** | "Enter the substitute's name." |
| screen reader | "**Sub 1 in spot 1** pinch-runs for #12 Altuve" | "Substitute for #44 Tucker — enter his name." |

Note the announcement too: it names `rowLabel(team, pIdx + runner)` for a row with no name, so
the only feedback the app does give is a placeholder.

**Fix.** Give it the same tail `markSub` has (app.js, end of `markPinchRunner` ~6035):

```js
  renderPitcherChange(team, pIdx, innIdx);
  updatePlayerStats(team);
  // Same hole F7 closed for SUB, in the function that never got it: the row that holds
  // the runner's name is `visibility: collapse` until it has one, so PR was a press with
  // no toast, no mark and no next step (F24).
  const nameInp = revealSubRow(team, pIdx);
  announce(rowLabel(team, pIdx + runner) + ' pinch-runs for ' + rowLabel(team, pIdx + subRowOf(ab)));
  showPlayNotice(nameInp ? 'Enter the pinch runner\'s name.'
                         : 'Pinch runner recorded — open Show sub rows to name him.');
  autoSave();
```

`revealSubRow` already drops its own `revealed` class on an empty blur, so a PR pressed by
mistake strands nothing.

**Verify.** Test: put a runner on, call `markPinchRunner()`, assert the slot's sub row carries
`revealed`, that `document.activeElement` is that row's name input, and that `#play-reject` is
showing. Mirror the existing `markSub` F7 test.

**Risk.** Very low. Additive, and the helper is already proven.

### F25 — the DP/FC/TP popup has no Cancel, and Escape refuses

**Symptom.** Press **DP** (or FC, or TP) by mistake. Key the fielders. The Runner Outcomes
popup opens — and there is no way out of it. No Cancel button. Escape says
*"Finish the open entry first."* A tap outside says the same. The only enabled control is
Confirm, so the only exit is to complete an entry you do not want and then undo it.

Confirmed live: the popup's full button list is
`Hold 1st, Safe 2nd, Safe 3rd, Safe Home, Out at 2nd, Out at 3rd, Out at Home, Safe 1st,
Safe 2nd, Safe 3rd, Out, Confirm` — no Cancel; and `display` is still `block` after an
Escape keydown.

**Root cause.** `ENTRY_IN_PROGRESS_POPUPS = ['runner-popup', 'outcome-popup']` (app.js:1774) —
both are must-answer, so both refuse Escape and the backdrop by design. F11b gave
`runner-popup` a Cancel with a caller-supplied rollback and wrote the reasoning at
app.js:2895-2900: *"There was no way out of this popup at all — no Cancel, and Escape did
nothing — so a play button pressed by mistake meant completing a wrong entry and then undoing
it."* `showRunnerOutcomePopup` (app.js:2286) never got the same treatment.

This is the concrete cost of the two popups being near-parallel implementations of one idea —
they are 259 and 311 lines, they solve the same problem, and a fix landed in one of them.

**Fix.** Mirror F11b. `showRunnerOutcomePopup` is reached from `applyPlay`, so like the two
`applyPlay` callers of `showRunnerPopup` it has a play and a result pitch already written and
needs the same rollback handed in. Add next to `#oc-confirm` (app.js:2407):

```js
  html += `<div style="display:flex;gap:6px;margin-top:6px">`;
  html += `<button id="oc-confirm" style="flex:1;…">Confirm</button>`;
  // Same trap F11b closed on the Advance Runners popup, in its sibling: DP/FC/TP pressed
  // by mistake could only be escaped by confirming a wrong entry and undoing it (F25).
  html += `<button id="oc-cancel" style="…">Cancel</button>`;
  html += `</div>`;
```

with `oc-cancel` calling the caller's rollback and `closePopupById('outcome-popup')`. Once it
has a Cancel, `outcome-popup` should also come off `mustAnswerPopups()` so Escape and the
backdrop close it — that is exactly the rule stated at app.js:1693-1697 ("Every other guarded
popup has a Cancel of its own … a tap outside is the same act as pressing it").

**Verify.** Test: enter a DP, press Cancel, assert the at-bat is back to empty, the result
pitch is gone, the popup is closed and the inning's outs are unchanged. A second test that
Escape now closes it, and a third that Confirm still records the double play — that last one
guards the rollback wiring.

**Risk.** Medium — the rollback has to take back the play *and* the pitch, which is why F11b
made it caller-supplied. Follow that shape rather than inventing a second one.

### F26 — a blocked runner option never says why

**Symptom.** In the DP popup, mark the runner **Hold 1st** and the batter **Out**. All three
of the batter's Safe options grey out at once, with nothing said. The reasons are perfectly
good — 1st is occupied, and 2nd or 3rd would put the batter ahead of a runner who started
ahead of him — but the popup does not say either, and on an iPad there is no hover to reveal
a tooltip. The scorer sees three dead buttons and, with F25 in force, no way out.

**Root cause.** `setOptionBlocked` (app.js:1487-1504) sets `disabled`, `opacity`, `cursor` and
three colours. No `title`, no `aria-disabled`, no message. Verified live — all three blocked
buttons returned `title: null, aria-disabled: null, aria-label: null`.

Compare the 5.08(a) bar a few lines away, which does this properly: `#oc-508a` explains itself
in words and tracks the selection (app.js:2475-2476), and `Safe Home` greys out *alongside*
the sentence rather than instead of it.

**Fix.** Give `setOptionBlocked` a reason and say it the way 5.08(a) is said:

```js
function setOptionBlocked(btn, blocked, why) {
  btn.dataset.blocked = blocked ? '1' : '';
  btn.disabled = !!blocked;
  // The 5.08(a) bar explains itself in words; a collision bar greyed out in silence, and
  // on a touch screen there is no hover to ask (F26).
  if (blocked && why) btn.title = why;
  else btn.removeAttribute('title');
  btn.setAttribute('aria-disabled', blocked ? 'true' : 'false');
  …
```

and pass the reason at the two call sites — `'1st is taken'` for an occupied base,
`'he would pass the runner ahead of him'` for an order conflict — surfacing it in a line under
the row the way `#oc-508a` does, since `title` alone is worth nothing on an iPad.

**Verify.** Test: build the DP state above, assert each blocked button carries
`aria-disabled="true"` and a non-empty reason, and that the reason line is visible.

**Risk.** Low. Additive.

## Tier 3 — ergonomics on the two devices this is used on

### F27 — everything in the scoreboard and lineup is a 17–26px touch target

**Symptom.** The play deck is properly sized for a finger. Nothing else is. Measured, live,
at each viewport (`getBoundingClientRect`, smallest of each kind):

| Control | 1194×834 | 1024×768 | 834×1194 | 390×844 | 844×390 |
|---|---|---|---|---|---|
| **linescore inputs** (18, editable) | 25×21 | 25×21 | 25×26 | **18×23** | **25×17** |
| **position selects** (27, dropdowns) | 39×21 | 39×21 | 39×21 | 33×21 | 33×21 |
| deck play buttons | 46×44 | 46×44 | 46×44 | 46×44 | **40×40** |
| team tabs | 72×34 | 72×34 | 72×34 | 63×36 | 65×30 |
| section buttons | 139×32 | 139×32 | 143×34 | 126×36 | 126×30 |
| deck handle | — | — | — | 350×32 | 789×**26** |
| +EI | 44×40 | — | — | — | — |

The 44px guideline is met by exactly one control family, and only above phone-landscape. The
worst offenders are the ones a scorer actually pokes at mid-game: the linescore R/H/E cells
are **editable inputs 17–26px tall**, and they get *smaller* as the screen does.

**Fix.** This is a real piece of work, not a number change — the linescore is a
fifteen-column table that has to fit beside the live readout, so the cells cannot simply grow.
The move that costs no width is a transparent pseudo-element hit area, which the codebase
already uses for exactly this on `+EI` (styles.css:782 — a 52×42 box on a smaller glyph):

```css
/* The R/H/E cells are edited with a fingertip and are 21px tall. Same trick as the
   +EI button at :782 — grow the target, not the cell (F27). */
.linescore td input { position: relative; }
.linescore td input::after {
  content: ''; position: absolute; left: 50%; top: 50%;
  width: 44px; height: 44px; transform: translate(-50%, -50%);
}
```

(`input` cannot carry `::after` — this wants a wrapper, or the pseudo-element on the `td` with
the input stretched to fill it. Settle that before starting.) The position `select` and the
phone-landscape deck buttons want the same treatment.

Rule this one before doing it — there is a real trade between the finger and the one-page fit,
and the fit is the feature.

**Verify.** Browser, at each of the five viewports: assert every interactive element's hit
box is ≥44px in both axes, or is on a documented exception list. This is a layout assertion,
so it cannot live in jsdom — it belongs in a browser check, listed here.

**Risk.** Medium. Hit areas that overlap will steal each other's taps; the linescore cells are
26px apart, so a 44px box on each *will* overlap and needs care.

### F28 — a phone in landscape matches the iPad block and the phone block at once

**Symptom.** At 844×390 — an iPhone Pro Max in landscape, the exact device the phone-landscape
block was written for — `matchMedia` reports **both**:

```
(min-width: 835px)                                                  -> true
(orientation: landscape) and (max-height: 500px) and (min-width: 740px) -> true
```

So the iPad block at styles.css:1263 applies *and* the phone block at 1773 applies. The phone
block is later so it wins where the two collide — but only where they collide. Every iPad rule
the phone block does not restate stays in force on a phone: the sticky `.deck-strip` at
`z-index: 120`, the compacted masthead, the 36px header buttons, `.sec-bar { flex-wrap: nowrap }`,
the `font-size: 0` caption. None of those were written with a 390px-tall window in mind.

This is the mirror of the drift `ui.js` warns about at 150-155 — there the risk is CSS and JS
disagreeing about what a phone is; here the stylesheet disagrees with *itself*.

**Fix.** Make the iPad block exclude the phone case, so the two are genuinely disjoint:

```css
/* Kept mutually exclusive with the phone-landscape block at :1773 — 844x390 matched both,
   so every iPad rule the phone block didn't restate was still in force on a phone (F28). */
@media (min-width: 835px) and (not ((orientation: landscape) and (max-height: 500px))) {
```

`not (…)` inside a media query needs Safari 16.4+; if that is too new for the target, invert
it as `@media (min-width: 835px) and (min-height: 501px)`, which is the same set and works
everywhere. Take F28 with F27 — the phone-landscape numbers in that table are partly this.

**Verify.** Browser: at 844×390 assert `matchMedia('(min-width: 835px)').matches === false`.
Then re-walk the five viewports and confirm nothing moved at the other four.

**Risk.** Medium — it changes which rules apply at a size that currently gets both, so the
whole phone-landscape layout wants re-checking after. That check needs screenshots.

## Tier 4 — the design system

### F29 — two independent z-index ladders

**Symptom.** There is no stacking scale, no token, and no comment defining tiers. There are
two ladders, written apart, and they interleave badly.

```
styles.css   1, 2, 3, 4, 120 (.deck-strip), 150 (.quick-bar docked),
             300 (.spray-popup, .info-body, .hdr-menu-panel),
             500 (.modal-overlay, .hotkey-modal), 600 (.game-summary-modal), 1000 (.banner)

app.js       180 (#popup-backdrop),
             300 (outcome, runner, k, base-picker, edit-play, move-runner, pos, pitcher, pos-change),
             400 (er-review, sub, dh, recompute, decision, play-reject)
```

Every gameplay popup sits at 300–400. Both of the big modals sit above them. So **any popup
opened from inside a modal renders underneath it** — F22 is one instance, and the Game Library
at 500 is the other route in. And `.banner` at 1000 outranks every dialog, so a storage
warning can paint over an open popup.

**Fix.** One scale, in tokens, in the stylesheet, consumed by both files:

```css
:root {
  --z-grid-sticky: 2;  --z-frozen-col: 3;   --z-frozen-head: 4;
  --z-deck: 120;       --z-deck-docked: 150;
  --z-menu: 300;       --z-modal: 500;      --z-modal-child: 700;
  --z-popup: 800;      --z-toast: 900;      --z-banner: 1000;
}
```

with the app.js popups reading `z-index: var(--z-popup)` from their `cssText`, the backdrop
one step below whatever it guards, and the banner kept top only if a banner really should
outrank a dialog — decide that rather than inherit it.

**Verify.** Test: assert no `z-index:` literal remains in app.js's popup `cssText` and that
every popup resolves above `.game-summary-modal`. Browser: open one popup from each modal and
check `elementFromPoint`.

**Risk.** Medium. It touches every popup, but each change is one declaration.

### F30 — 21 of 41 tokens are shadowed, and two are named the opposite of what they are

**Symptom.** There are three `:root` blocks (styles.css:28, 875, 1433). The second
unconditionally redefines most of the first by source order — not a theme switch, just a
later declaration. Read live from the resolved cascade:

```
--navy:        #003278            -> var(--rb-blue)
--cream:       #f3f2f2            -> var(--paper)
--border:      #201e1d            -> var(--rb-blue)
--green:       #17693a            -> var(--rb-blue)      <- a token called green resolves to navy
--gold:        #f4efe4            -> var(--rb-white)     <- a token called gold resolves to white
--select:      #eef3fb            -> rgba(192,17,31,0.12)
--text:        #201e1d            -> var(--rb-blue)
--text-light:  #6f6a63            -> rgba(0,50,120,0.72)
… 21 in total
```

So the base palette's *values* are dead weight — every one of them is overwritten — while its
*names* live on and now lie. `--gold` is the colour of the text on the red total cell
(styles.css:216) and it is white. `--green` is used for a runner tint and it is navy.

Five more tokens are declared and never referenced anywhere: `--navy-light`,
`--accent-light`, `--gold-light`, `--blue-deep`, `--sa-b`.

There is also no spacing, radius, shadow or type-scale token at all — every one of those
values is a literal, which is why there are 24 distinct font sizes and 26 `!important`s.

**Fix.** Collapse to one `:root`. Keep the `--rb-*` brand primitives as the source of truth,
give the semantic layer names that survive a re-skin (`--ink`, `--paper`, `--rule`,

five unused, and delete the shadowed base values outright rather than leaving two palettes in
the file. The three mutually exclusive "keep this block last" instructions (styles.css:858,
1203, 1389) go away with it, and so does the re-laddering at 1174-1189 they force.

**Verify.** No behaviour change is intended, so the check is that nothing moved: screenshot
all five viewports before and after and diff. Add a test asserting every `var(--x)` in
app.js and styles.css resolves to a non-empty value on `:root`.

**Risk.** Medium-high by blast radius, near-zero by logic. Do it in one commit, not spread out.

### F31 — `--font` and `--heading` are identical, and `--mono` never renders

**Symptom.** Read live:

```
--font:    'Graduate', "Source Serif 4", Georgia, serif
--heading: 'Graduate', "Source Serif 4", Georgia, serif      <- byte-identical to --font
--mono:    'Graduate', 'JetBrains Mono', 'SF Mono', Consolas, monospace
```

Two consequences. There is **no body/heading distinction** anywhere in the app — the two
tokens are the same string, so every `font-family: var(--heading)` is decoration with no
effect. And **JetBrains Mono never renders**: Graduate is first in `--mono`, so the 31KB
font is downloaded, precached by the service worker, and only ever used if Graduate fails to
load. Graduate is also a single-weight display face with no true italic, so every
`font-weight: 600/700` and `font-style: italic` in the stylesheet is synthesised.

The pitch marks, the count and the fielder keypad are all `var(--mono)` — they are the places
tabular figures matter most, and they are getting a display face instead.

**Fix.** styles.css:936-938:

```css
  --font: "Source Serif 4", Georgia, serif;
  --heading: 'Graduate', "Source Serif 4", Georgia, serif;
  /* Graduate has no tabular figures and one weight; the mono stack exists for the pitch
     marks and the count, so it must not start with the display face (F31). */
  --mono: 'JetBrains Mono', 'SF Mono', Consolas, monospace;
```

This one changes how the whole card looks — it is a design decision, not a bug fix. If
Graduate everywhere is the intended house style, then say so and delete JetBrains Mono and its
`@font-face` instead; what should not stand is downloading and precaching a font that cannot
render.

**Verify.** Screenshots of all five viewports, plus a check that the four `@font-face` families
each have at least one element resolving to them.

**Risk.** Low mechanically, high visually. Wants a ruling before a commit.

### F32 — no overlay is a dialog

**Symptom.** Of the overlay surfaces present in the DOM, **none** carries `role="dialog"`,
`aria-modal`, `aria-labelledby` or `aria-label`. Measured live: `overlaysWithRole: 0`. The
same is true of the fourteen popups built on demand — they are all
`document.createElement('div')` plus a `style.cssText`, with no role and no label.

There is also no focus trap, no focus restoration and no `inert` on the background, so Tab
walks straight out of an open popup into the card behind it, and closing a popup leaves focus
wherever it landed. Across 8,161 lines app.js sets exactly one `role`, two `aria-selected`,
three `aria-current` and two `aria-label`.

The card itself is much better served than the dialogs — `describeCellForScreenReader`,
`announce()` and `#a11y-live` are careful work. It is only the overlays that were left out.

**Fix.** One helper, called from `openPopup` (app.js:1720), so every popup gets it at once
rather than fourteen edits:

```js
function openPopup(popup, labelId) {
  popup.setAttribute('role', 'dialog');
  popup.setAttribute('aria-modal', 'true');
  if (labelId) popup.setAttribute('aria-labelledby', labelId);
  popup.dataset.returnFocus = document.activeElement ? … : '';
  …
```

plus a `keydown` trap on Tab within `blockingPopup()`, and restoring focus in `closePopup`.
Every generated popup already emits a title `<div>` first — give those an id and pass it.

**Verify.** Tests: for each popup id, assert `role="dialog"` and `aria-modal="true"` after
`openPopup`, and that `aria-labelledby` points at an element with text. Tab-cycling and focus
restoration need a browser check.

**Risk.** Low if done in `openPopup`. Do not do it fourteen times.
